# Stuudio Aeg — juuksurisalongi broneerimissüsteem

SaaS-õppeprojekt: kasutaja saab registreeruda, sisse logida, vaadata salongiteenuseid ja vabu aegu, broneerida aja ning näha enda broneeringuid. Frontend on Vite + vanilla JavaScript, backend PocketBase, juurutus Coolify abil.

**Current state:** frontend and PocketBase schema/setup script are prepared. **Not yet verified live.** Stripe and Google/GitHub OAuth **are not implemented**. No real payment is charged. Do not report those as completed in coursework.

## Tehniline arhitektuur

- Frontend (Vite) is a separate Coolify application and talks to PocketBase over REST using the JS SDK.
- PocketBase is a separate Coolify service. Persist `/app/pb_data` with a Docker volume (provided by the Coolify PocketBase template). The template's `/app/pb_hooks` volume is optional for this initial MVP.
- `services` and `available_slots` can be read publicly; `bookings` are readable by their owners only. A unique SQLite index on `bookings.slot` prevents double-booking at the database level, including concurrent attempts.
- Service and availability management is performed by the salon administrator from PocketBase Admin in the initial MVP.
- Demo services and slots are generated by the setup script; replace them with real opening hours and capacity before real use.

## Kohalik käivitamine

```bash
npm install
cp .env.example .env
# edit VITE_POCKETBASE_URL in .env
npm run dev
```

Never put the PocketBase superuser email or password in `VITE_*` environment variables, GitHub, a public frontend build, or ChatGPT. Only set `VITE_POCKETBASE_URL` to the public, trusted HTTPS PocketBase URL.

## PocketBase seadistamine

1. First resolve HTTPS warnings for the PocketBase domain. A DNS match alone does not guarantee a valid certificate. Don't sign into PocketBase through a browser TLS warning.
2. Sign into PocketBase Admin as the *first* superuser with a legitimate, freshly generated install link, or use PocketBase's `superuser upsert` command in your OWN container. Do not share setup links, superuser tokens or passwords.
3. On a trusted local terminal, set `PB_URL`, `PB_ADMIN_EMAIL`, `PB_ADMIN_PASSWORD` as temporary environment variables, then run `npm run setup:pb`. The script will create the schema, sample salon services and sample time slots. It won't overwrite an existing collection. **Run only on your own dedicated PocketBase**, never on another student's database.
4. Inspect `services`, `slots`, `available_slots`, `bookings` and `users` collections in Admin. Check API rules, including that different users cannot see each other's bookings.
5. Note: the setup script needs access to the PocketBase Admin API via trusted TLS. It is intentionally not bundled in the frontend and must never run in the browser.

## Coolify deploy

1. Create **a new application in your own project** from this GitHub repository via the `Git Repository (with GitHub App)` resource type, if your GitHub account is connected; otherwise use a public Git repository resource. Configure auto-deploy/webhooks if available.
2. Build pack: Nixpacks or Docker-compatible Vite static deployment; build command `npm ci && npm run build` (or `npm install && npm run build` if no lockfile yet); output directory `dist`. **Do not use port 8080 merely because PocketBase uses 8080 — frontend and backend are separate.**
3. Add `VITE_POCKETBASE_URL=https://...` as a **build-time** environment variable for the frontend. Rebuild after changing it; Vite embeds `VITE_*` at build time.
4. Assign a frontend domain and enable valid HTTPS. Verify the frontend can reach PocketBase without TLS warnings or CORS errors.
5. Test account registration, signing in, a booking, viewing only your own bookings, and a second user attempting the same slot. Restart PocketBase and verify the booking is still present.

## Google/GitHub OAuth and Stripe — extension work

PocketBase email/password is the initial login option. If coursework requires OAuth for the target grade, configure Google/GitHub through PocketBase OAuth2 providers and a browser login flow. Booking creation is **not a payment**: for Stripe Test Mode integrate a trusted server-side Checkout + webhook which confirms payment before marking a booking paid. Never accept a browser-supplied `paid=true` field. These extensions have not been implemented yet.

## Andmemudel

| Collection | Fields | API rules |
|---|---|---|
| users (auth) | name, email, password | public registration; user can see own profile |
| services | name, description, price_eur, duration_min, active | published services public read, admin write |
| slots | service, starts_at, ends_at | admin-managed, private direct API |
| bookings | user, slot | owner reads/creates only, admin manages; unique(slot) |
| available_slots (view) | id, service, starts_at, ends_at | public read of only unbooked future slots; no customer personal data |

Known MVP limitations: no payments, no OAuth, no self-service booking cancellation, no staff calendar, no server-side validation of time ranges beyond unique slot and PocketBase schema. For a production system add server-side checks for slot existence, future time, service availability, booking window and rate limiting. This is a coursework prototype, **not ready to process real customer data or payments**.
